# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

Compliance Test Kit (CTK) for TM Forum ODA Components. Four test suites (NodeJS, Mocha + Chai):

- **L1** promotes a component from Stage 1 to 2 (conforms to design guidelines); **L2** from Stage 2 to 3 (meets functional scope of a "Golden Component").
- **static** suites validate the component envelope YAML; **dynamic** suites query a live Kubernetes cluster (and, for L2, run API CTKs against the deployed component).

## Commands

```
npm install
npm run L1-static   -- <file.component.yaml>
npm run L1-dynamic  -- <file.component.yaml> [-n|--namespace <ns>] [-H|--header <header>]
npm run L2-static   -- <file.component.yaml>
npm run L2-dynamic  -- <file.component.yaml> [-n <ns>] [-H <header>]
```

- Namespace defaults to `components` (or the `NAMESPACE` env var).
- The component YAML is normally generated with `helm template <release> <chart> > file.component.yaml`.
- Dynamic suites use the default kubeconfig (`kc.loadFromDefault()`), so the component must already be deployed to the current cluster.
- There is no separate lint/test runner: `npm test` just runs L1-static. ESLint config (`standard`) exists in `.eslintrc.json`; there is no npm lint script, so run `npx eslint <file>`.
- There is no per-test CLI option. To run a single test, use `it.only` / `describe.only` in the `*ValidationTests.js` file, or run Mocha directly with `--grep` after setting `process.env.components` (the runner sets this; tests read `process.env.components`, `NAMESPACE`, `HEADER`).

## Architecture

Each suite is a pair of files at the repo root:

- `<Level>-<static|dynamic>-CTK.js`: runner. Parses CLI args (`-n`, `-H`), exports them via `process.env` (`NAMESPACE`, `HEADER`, `components`), then creates a `Mocha` instance and `addFile`s the tests file. (L2-dynamic falls back to every `./components/*.yaml` if no file is passed; the others take `process.argv[2]`.)
- `<Level>-<static|dynamic>ValidationTests.js`: the actual `describe`/`it` tests. Tests are generated by looping over `process.env.components` at load time, so test structure is built dynamically per component file.

Key points that span files:

- **L2 uses Golden Components.** `L2-dynamicValidationTests.js` reads the deployed Component CR (`oda.tmforum.org` `v1alpha4`, via `CustomObjectsApi`), derives the golden file name from `spec.type` + `spec.version` (e.g. `TMFC001-productcatalogmanagement-v0-0-3.yaml`) in `golden-components/`, and for each `coreFunction.exposedAPIs` entry runs the matching API CTK. Golden components are mastered externally at tmforum-oda/oda-components-specs.
- **API CTK lookup is hardcoded.** The `ctkPaths` map at the top of `L2-dynamicValidationTests.js` maps API title and version to a folder under `api-ctk/`. Supporting a new TMF API means adding a CTK folder and a `ctkPaths` entry. The deployed component's API is matched to the golden one by OpenAPI `info.title` + `info.version`.
- **`api-ctk/*`** are self-contained Postman/Newman-based TMF Open API CTKs, each with its own `package.json`, `config.json` (URL gets overwritten by the L2 test from the component) and `ctk/` folder. `APITestRunner.js` at the root is the glue that runs them programmatically. Their results go to `results/` (gitignored, along with `api-ctk/*/jsonResults.json` and `*.html`).
- **Supported apiVersions** for the static tests are hardcoded lists inside the test files (e.g. `oda.tmforum.org/v1alpha1..v1alpha3` in L1 static); `v1alpha1..v1beta1.component.yaml` at the root are sample component envelopes for each version. Check these lists when adding a new CRD version.
- **`TMF653_ServiceTest/`**: a separate swagger-codegen NodeJS server (TMF653 Service Test API) with its own `package.json`/Dockerfile; not part of the CTK runners.
- **`BDDandTDD/`**: separate Cucumber (BDD) experiment for TMFC001 with its own `package.json` (`npm start` runs `cucumber-js`); not part of the CTK runners.
